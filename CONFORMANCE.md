# Protocol coverage

This example targets the [OMP v0.5 editors’ draft](https://github.com/The-AI-Disclosures-Project/Open-Memory-Protocol/blob/81e99b79480af77528c8499b306920c78d1c6d76/working-group/exchange-and-runtime/2026-11-06-working-spec-v0.5.md), with the minimal profile. The draft is not an adopted standard. Its manifest, reference addressing and runtime bindings are still evolving. `/fmp/info` describes the supported subset and local conventions. This repository does not claim full OMP conformance.

## Compliance target and checklist

The user-selected scope is **all core requirements and the profiles this implementation supports**, rather than every optional profile. The target is pinned to upstream revision `81e99b79480af77528c8499b306920c78d1c6d76`; a draft update requires a new review. Normative statements remain proposed under §0.3. The server advertises only `minimal`; the SDK also implements the Markdown loading behavior described below. No official certification or complete implementation of every proposal is claimed.

## Memory and lifecycle

The API validates required metadata, all currently typed optional standard fields, contributor records and calendar dates. Timestamps use ISO 8601's extended date/time form with `Z` or an explicit offset. Unknown JSON fields, including nested contributor and reference extensions, survive exchange. Evidence remains a list of strings or reference objects; links remain a list of objects because their detailed schemas are open in the draft.

New writes require an explicit `id` and `kind` for a supplied self-declared contributor, or record the known `system:omp-cloudflare` process. The latter records that the system stored or changed the memory; it does not invent the original author or an accountable human. ID prefixes never establish contributor kind. Provenance timestamps record actual write time even when `created_at` is historical. The Pi chat tool identifies itself as `{id: "agent:pi-chat", kind: "agent"}`. Updates append contribution records and cannot replace provenance. Deletes leave content-free markers recording a writer, time and reason; content remains in Git history. Imported memories keep their original provenance, including its absence, and remain immutable locally.

Ordinary HTTP and MCP reads and searches exclude future, expired and superseded records. HTTP read accepts `include_inactive: true` to inspect an inactive current record explicitly. This does not request a previous Git revision, and applicability is still checked. Supersession follows recognized `supersedes` edges whose memories have become effective; expiry of the replacement does not revive the superseded record. Supersession is local to an origin unless an edge explicitly supplies its target's `origin`.

Older versions could store malformed standard metadata. Loading an existing store preserves those complete records in an internal `quarantined` array, while valid memories remain available. Search reports `quarantined_records`; export reports the count and reason under `manifest.x_omp_omissions`. Quarantined data is excluded from memory use and exchange. Repair it in the source Artifacts repository, retaining the original identity and recording the correction; it is not silently converted into invented metadata or deleted.

## References and exchange

The experimental `omp-references/0.1` convention (previously named `omp-cloudflare-references/0.1`) recognizes `{target, origin?}` objects in links and evidence and exact `[[identifier]]` references in plain text or Markdown. A `target` is an opaque memory identifier, including when it contains colons. External sources can use `{uri: "https://..."}`; free-form evidence strings and other object shapes remain opaque. These conventions are experimental, not adopted OMP syntax.

Missing recognized targets are retained. HTTP reads/searches and MCP results expose `dangling_references`; export exposes `manifest.x_omp_dangling_references`. These diagnostics are computed separately, so resolving a target does not rewrite the source record or invalidate its concurrency token.

Exports keep identifiers unique when several origins contain the same identifier. Collision aliases are applied consistently to recognized links, evidence and inline references. `x_omp_identity_map` restores original identities and references on import. Unrecognized reference shapes survive unchanged; another implementation must understand this experimental convention to reconstruct them. Portable checksums are preserved: an export that would change a checksummed record fails rather than emitting a stale checksum. Export one origin separately with `?origin=<URL-encoded-origin>` in that case. Local authoring/update does not accept portable `checksum` or `version` fields; use import to retain externally authored values. The local response `version` is a concurrency token, not an OMP revision comparator.

The supported exchange intent is `copy`, with `minimal` snapshots or selections. Absence never deletes data. Import provides receipts and preserves original identities across retries. Each HTTP export page is labelled `selection` and carries `x_omp_pagination` metadata. Collect every page against the same commit before treating the result as a snapshot. The bundled client and browser exporter do so and remove the pagination marker when complete. A page alone must not be treated as a complete deletion ledger. Tombstone transfer is incremental, rather than an atomic cross-store transaction.

## Markdown directory loading

The provider-neutral SDK implements the draft’s §10.2 loading pattern through `exportMarkdown` and `openMarkdownDirectory`: root `MEMORY.md`, immediate-child summaries, deferred deeper indexes/bodies and selective reads. Full JSON metadata is carried in sidecars; original `memory.path` remains distinct from the projection filename. The experimental `omp-markdown/0.1` encoding declares `losses: []` and reconstructs the original supported copy envelope, including identities and tombstones. Keep all sidecars when transferring it.

The draft leaves the concrete Markdown encoding open. This repository’s index/sidecar names are a local proposal, not finalized interoperable syntax. The HTTP API continues advertising its minimal copy binding; `pnpm memory:markdown` composes its paginated snapshot with the SDK projection. It does not add Markdown upload routes, local edit reconciliation or synchronization. [API and format details](packages/omp-sdk#export-and-load-markdown-progressively).

## Credentials and supported profiles

The SDK’s copy and Markdown export boundaries reject recognizable credentials under §8.6. The app’s write, update, import and export boundaries additionally check the deployment access key. These boundaries reject recognizable credential fields, labelled password/key assignments, common key formats, private-key material, credential-bearing URLs and the deployment access key. Rejections do not echo the credential. Export also checks existing records. This is a deterministic rejection policy, not a universal classifier: arbitrary unlabelled secrets can resemble ordinary text. Do not submit secrets as memory. The policy rejects a whole operation rather than silently redacting unknown metadata.

Audit, secure forgetting, ACL enforcement, moves, automatic hooks and real-time sync remain unsupported. The personal/company stores share one operator token. Git history provides persistence and revision inspection; it does not by itself establish the audit profile or erasure guarantees.

## Verification

`pnpm verify` includes strict checks, unit tests, builds and isolated HTTP/MCP/concurrency/exchange tests. The `conformance:roundtrip` script adds regression checks for malformed metadata, provenance, lifecycle, dangling references, credential rejection and export completeness. These checks verify this implementation's supported contract; they are not an official OMP certification suite.

The reusable implementation lives in [`packages/omp-sdk`](packages/omp-sdk). Core validation is independent of this deployment’s quotas and credential policy. Exchange/reference and Markdown conventions have experimental package entry points. Cloudflare HTTP contracts, runtime activation policy and HTTP status mapping live entirely in the app. Older envelopes keep their convention tags on import; identity maps and unknown manifest metadata remain accepted.
